# 真机渲染栈落地实录（R36H ProMax / RK3326 / Mali-G31）

**结论先说**：网页前端已经在真机上真的画到屏幕上了，ES 被顶掉。
最终可用组合是：

```
weston --backend=drm-backend.so --use-pixman --idle-time=0 --tty=1 \
       --socket=wayland-vagaretro
+ LD_PRELOAD=/opt/vagaretro/lib/libgbm-shim.so
+ LD_LIBRARY_PATH（可选，见第 7 条）
+ XDG_RUNTIME_DIR=/run/vagaretro（属主 root、0700）
+ 启动前把 tty1 从 KD_GRAPHICS 复位成 KD_TEXT
→ python3 + GTK3 + WebKitGTK 全屏宿主连上去渲染
```

下面是把上面这条命令跑通之前踩掉的 **7 个真机坑**。按踩到的顺序排，每条都写了
「现象 → 根因 → 修法」，都在真机上实测过。

## 0. 前置：渲染栈根本不在镜像里

现象：日志 `/var/log/vagaretro-front.log` 里

```
native: 没有 weston
cog 失败，试 chromium
所有渲染路径都失败，回退 ES
```

根因：dArkOS 镜像里**一个浏览器引擎都没有**（只有 mpv），weston / WebKitGTK 都没装。
另外 `libgtk-3-0` 装了但 **`gir1.2-gtk-3.0` 没装**，所以 Python 会报
`Namespace Gtk not available`。

修法：设备联网后跑

```bash
sudo bash /opt/vagaretro/tools/install-browser.sh --check   # 先体检
sudo bash /opt/vagaretro/tools/install-browser.sh           # 装，约 104 MB
```

实测 **1 分 47 秒**装完：`weston 5.0.0` + WebKit2 绑定 2.28 + `/dev/dri/card0`
与 `renderD128` 齐备。eoan 源走 `old-releases.ubuntu.com`（镜像里默认就配了）。

## 1. `sudo` 会清掉环境变量（`env_reset`）

现象：

```
weston: fatal: environment variable XDG_RUNTIME_DIR is not set.
```

根因：启动器里明明 `export XDG_RUNTIME_DIR=...` 了，但 weston 是经 `sudo` 拉起的，
而 **sudo 默认 `env_reset`，会把环境变量全部清空**。宿主同样会中招。

修法：环境变量一律用 `env` 递进去，不依赖 sudoers 的 `SETENV` / `env_keep`
（ArkOS 只给了 `ark ALL=NOPASSWD: ALL`）：

```bash
sudocmd="sudo -n"
$sudocmd env XDG_RUNTIME_DIR=/run/vagaretro WAYLAND_DISPLAY=... weston ...
```

`sudo env A=b cmd` 里 `env` 是个普通程序，完全绕开 sudo 的环境策略。

## 2. `XDG_RUNTIME_DIR` 的属主必须 == 运行 weston 的 uid

现象：weston 启动时 stat 这个目录，发现属主不对就直接 fatal。

根因：weston 会检查该目录的属主是否等于 `getuid()`。weston 以 root 跑，
目录若由 `ark` 创建，属主是 `ark` → 不符。

修法：目录交给 root 建，并放在 `/run`（tmpfs，重启自动清，不会残留上一轮的属主）：

```bash
$sudocmd mkdir -p /run/vagaretro
$sudocmd chown -R root:root /run/vagaretro
$sudocmd chmod 700 /run/vagaretro
```

## 3. libgbm 是 libmali 的，缺 6 个 mesa 新符号

现象：

```
Loading module '.../libweston-5/drm-backend.so'
Failed to load module: undefined symbol: gbm_bo_get_plane_count
fatal: failed to create compositor backend
```

根因：这台机器上

```
/usr/lib/aarch64-linux-gnu/libgbm.so.1 -> libMali.so
        -> libmali-bifrost-g31-rxp0-wayland-gbm.so
```

这个 blob 只导出 **22 个** `gbm_*` 符号，而 weston 5.0 的 `drm-backend.so` 需要
mesa 2017 年后才加的 **6 个** modifier / 多平面 API：

| 缺失符号 | 语义 |
|---|---|
| `gbm_bo_get_plane_count` | 平面数 |
| `gbm_bo_get_stride_for_plane` | 某平面的 stride |
| `gbm_bo_get_offset` | 某平面的偏移 |
| `gbm_bo_get_modifier` | 布局 modifier |
| `gbm_bo_get_handle_for_plane` | 某平面的 handle |
| `gbm_surface_create_with_modifiers` | 带 modifier 建 surface |

> 注意：**缺的是 6 个，不是一个。** 早先的记录只写了 `gbm_bo_get_plane_count`，
> 那只解决了"能加载"，跑起来还会在别的地方炸。

修法：写一个 **libgbm shim**，只实现这 6 个，按「单平面 + 线性布局」语义，
用 `LD_PRELOAD` 注入，**系统库一个字节都不动**。源码 `build/libgbm-shim.c`，
编译产物固化在 `payload/opt/vagaretro/lib/libgbm-shim.so`。

实测对照（设备上 `ldd -r`）：

```
[A] 不带 shim：drm-backend 未解析符号 = 6
[B] 带 shim  ：(空 —— 全部解析成功)
```

### 3.1 shim 怎么链接（两个反例 + 正解，很重要）

这里连续错了两次，值得单独记：

**反例 A：只用 `extern` 声明，不链接。**

```c
extern uint32_t gbm_bo_get_stride(void *bo);   /* 指望运行时去 libMali 找 */
```

结果：

```
weston: symbol lookup error: libgbm-shim.so: undefined symbol: gbm_bo_get_stride
```

根因：weston 是用 `dlopen(RTLD_LOCAL)` 载入 `drm-backend.so` 的，
**libMali 因此不在全局符号域里**；preload 进来的 shim 里那些未定义符号既不在全局域、
也不在自己的 `DT_NEEDED` 里 → 运行时找不到。
（而且这个错是在 weston 已经选好 EGL config、正要建 surface 的那一瞬间才炸的，
很有迷惑性。）

**反例 B：改用 `dlopen` + `dlsym`。**

```c
h = dlopen("libgbm.so.1", RTLD_NOW | RTLD_GLOBAL);
f = dlsym(h, "gbm_bo_get_stride");
```

结果：编出来的 shim 需要

```
dlopen@GLIBC_2.34
dlsym@GLIBC_2.34
```

而设备是 **glibc 2.30**（`dlsym` 还在 `libdl.so.2` 里，libc 里根本没有），
一加载就 `version GLIBC_2.34 not found`。
根因：WSL 里的交叉工具链太新，glibc 已到 2.4x，把 dl 并入 libc 了。

**正解：链接设备上那份 libMali.so，让它成为 shim 的 `DT_NEEDED`。**

```bash
# 1) 先把设备的 libMali.so 拉下来（它没有 SONAME，DT_NEEDED 记的就是文件名）
sshpass -p <设备密码> scp <用户名>@<设备IP>:/usr/lib/aarch64-linux-gnu/libMali.so build/mali/

# 2) 编译时链上它
aarch64-linux-gnu-gcc -O2 -shared -fPIC -Wall -o libgbm-shim.so libgbm-shim.c \
    -Wl,--no-as-needed -L./mali -l:libMali.so
```

这样符号解析走 **shim 自己的依赖域**，既不依赖全局域，也不用 dlsym。
自检（`build/build-shim.sh` 会自动查）：

```
未定义符号: gbm_bo_get_stride / gbm_bo_get_handle / gbm_surface_create  ← 由 libMali 解析
需要的版本: GLIBC_2.17 only        ← 绝不能出现 GLIBC_2.34
DT_NEEDED : libMali.so, libc.so.6
```

> `-z now` 是 Ubuntu/Debian 的默认（BIND_NOW），所以所有符号必须在加载时就能解析。
> 正因为 libMali 是 shim 的 `DT_NEEDED`，加载顺序上它一定先于 shim 完成映射，OK。

## 4. weston 的 legacy launcher 要求 VT 是文本模式

现象：

```
logind: failed to get session seat
logind: cannot setup systemd-logind helper (-61), using legacy fallback
/dev/tty1 is already in graphics mode, is another display server running?
fatal: drm backend should be run using weston-launch binary, or your system should provide the logind D-Bus API.
```

根因分两层：

1. 服务里跑（`User=ark`、没有分配 tty）拿不到 logind 的 seat，weston 退到 legacy 路径，
   legacy 路径**必须有一个 tty**（要传 `--tty=N`，否则先报 `<stdin> not a vt`）。
2. 有了 tty 之后，它还会 `KDGETMODE` 检查该 VT 是不是文本模式。
   **ES 和 weston 自己非正常退出都会把 VT 留在 `KD_GRAPHICS`，不会还原** ——
   于是第二次启动必然失败，形成自我锁死。

修法：启动 weston **之前**，把目标 tty 强制切回 `KD_TEXT`。
启动器里的 `reset_vt_text()` 就是干这个的（每次尝试前都调一次）。

**坑中坑**：vt ioctl 的参数约定**不一致**，写错了会拿到 `EINVAL`：

```python
# KDSETMODE(0x4B3A) 收【裸值】
fcntl.ioctl(fd, 0x4B3A, 0)        # ✔
fcntl.ioctl(fd, 0x4B3A, b"\0\0\0\0")   # ✘ EINVAL —— 这是在传指针

# KDGETMODE(0x4B3B) 收【指针】
buf = fcntl.ioctl(fd, 0x4B3B, b"\0\0\0\0")   # ✔
```

另外设备上 `/usr/bin/weston-launch` 是存在的（setuid root），
理论上它自己会处理 VT 这一套，可以作为备选路线。

## 5. 启动器以 `ark` 跑，检查 root 进程 / 0700 目录会失败（判死自己的 weston）

这条最隐蔽，现象是：

```
[01:02:46.014] launching '/usr/lib/weston/weston-desktop-shell'
[2026-09-14 01:02:46] native: weston 第 2 次启动失败
[01:02:46.146] caught signal 15
```

weston **明明完整起来了**（Output enabled + desktop-shell 都拉起来了），
启动器却在 **250 毫秒后**把它判为失败并 kill 掉。

根因：启动器以 `ark` 运行，而 weston 是 root 进程、`XDG_RUNTIME_DIR` 是 `0700 root`：

| 检查 | ark 看到的结果 | 后果 |
|---|---|---|
| `kill -0 <root pid>` | **EPERM**（不是 ESRCH） | shell 里当"失败"→ `\|\| break` 立刻跳出等待循环 |
| `[ -S /run/vagaretro/xxx ]` | **EACCES**（目录不可穿越） | 永远为假 |

修法：这两项检查都必须经 sudo 走 root。

```bash
proc_alive() {
    if [ -n "$SUDO" ]; then $SUDO kill -0 "$1" 2>/dev/null; else kill -0 "$1" 2>/dev/null; fi
}
have_socket() {
    if [ -n "$SUDO" ]; then $SUDO test -S "$RTDIR/$WAYLAND_DISPLAY" 2>/dev/null
    else test -S "$RTDIR/$WAYLAND_DISPLAY" 2>/dev/null; fi
}
```

## 6. GL 合成起不来：真凶是 gbm shim 的 DT_NEEDED（2026-09-14 结案）

关掉 pixman、想走 GL 硬渲染时撞上的：

```
Loading module '.../gl-renderer.so'
failed to initialize display
EGL error state: EGL_NOT_INITIALIZED (0x3001)
failed to initialize egl
```
stderr：
```
file /dev/mali0 is not of a compatible version (user 10.6, kernel 11.7)
Failed creating base context during opening of kernel driver.
```

### 6.1 曾经（错误）的判断

第一轮排查得出的结论是"设备上两个 blob 的 DDK 都跟内核对不上，所以 GL 用不了，
只能 `--use-pixman`"。**这个结论是错的**，错在把 `user 10.6` 归给了
`gl-renderer.so` 解析到的那个 blob。实际上 gl-renderer 解析得**没有错**。

### 6.2 实际的两套 blob

| 路径 | 大小 | 内部版本 | wayland-egl | EGL 能否初始化 |
|---|---|---|---|---|
| `/usr/local/lib/aarch64-linux-gnu/libmali-bifrost-g31-rxp0-gbm.so` | 40.8 MB | `U:r13p0-01rel0` | **没有** | **可以** ✅ |
| `/usr/lib/aarch64-linux-gnu/libmali-bifrost-g31-rxp0-wayland-gbm.so` | 38.9 MB | OpenCL `v1.r6p0` | 有 | 不行 ❌ |

`/usr/local/lib/aarch64-linux-gnu` 在 `/etc/ld.so.conf.d/*` 里排在前面，
所以 weston 的 `gl-renderer.so` 链到的 `libEGL.so.1` **本来就是对的那个（r13p0）**。

怎么一眼看出 blob 的版本：`strings <blob> | grep -E 'r[0-9]+p[0-9]'`
（r13p0 那份还会带一句 `DDK compatibility check`）。

### 6.3 真凶：shim 拉进来的老 blob 抢走了符号

第 3 节里，为了解析 `gbm_bo_get_stride` 这些符号，`libgbm-shim.so` 的
`DT_NEEDED` 里**硬链接了 `libMali.so`**。而 `libMali.so`（大写 M）
**只在 `/usr/lib/aarch64-linux-gnu/` 下存在**（指向老 blob）；
`/usr/local/lib/aarch64-linux-gnu/` 里只有小写 `libmali.so` —— Linux 区分大小写，
所以这个名字**必然**解析到老 blob。

后果链：
1. shim 被 `LD_PRELOAD` 注入 → 它的依赖也进**全局符号域**；
2. 全局符号域排在 `gl-renderer.so` 自己的依赖之前；
3. 于是 `eglGetDisplay` 解析到**老 blob** → `eglInitialize` 撞上版本检查
   → `user 10.6, kernel 11.7`。

也就是说：**是这个 shim 把 GPU 路径堵死的**，而且它堵得很安静 ——
不打开 GL 渲染你永远看不到这条报错。

### 6.4 修法（一行软链 + 一个环境变量，不用重编 shim）

```bash
ln -sfn /usr/local/lib/aarch64-linux-gnu/libmali-bifrost-g31-rxp0-gbm.so \
        /opt/vagaretro/lib/libMali.so
# 然后只给 weston 加环境变量：LD_LIBRARY_PATH=/opt/vagaretro/lib
```

`LD_LIBRARY_PATH` **先于** `ld.so.conf` 搜索，所以 shim 的 `DT_NEEDED`
就落到新 blob 上了，shim 和 gl-renderer 用的是**同一个** blob。

**只给 weston，不要给宿主**：宿主（GTK/WebKit）走 `wl_shm` 软件合成就够用，
而且新 blob 根本不导出 `wl_egl_window_*`，给了它反而把宿主拖进一条走不通的链。

落地位置：`vagaretro-front.sh` 的 `run_native()` 里，变量名 `LIBPFX`。

### 6.5 验证（零依赖，不用编译器）

设备上 **没有 libc 头文件**（`gcc` 在但 `dlfcn.h` 没有），所以探针用 ctypes 写，
直接 `ctypes.CDLL(<blob绝对路径>)` 逐个试：`tools`/`build/eglprobe.py`。

一个必须注意的细节：**这批 2020 年的 Mali blob 里没有 `eglGetPlatformDisplayEXT`**，
只有 `eglGetPlatformDisplay`（甚至连这个都不一定有）。老写法是把
`gbm_device` 指针**直接当 native display** 交给 `eglGetDisplay()`：

```python
dpy = egl.eglGetDisplay(gbm_dev)      # ← 不是 eglGetPlatformDisplayEXT
assert egl.eglInitialize(dpy, ...)    # 版本检查就在这一步
```

实测结果：r13p0 那份 `eglInitialize OK -> EGL 1.4 / 1.4 Bifrost-"r13p0-01rel0"`
且 `eglCreateContext` 也过；老 blob 直接 `eglGetDisplay` 返回 NULL。

修完后的 weston 日志：
```
EGL version: 1.4 Bifrost-"r13p0-01rel0"
GL renderer: Mali-G31
Output 'DSI-1' enabled with head(s) DSI-1
```
而且**没有**出现"第 2 次尝试"（说明第 1 次就起来了）。

### 6.6 收益与代价

- 收益：合成从 CPU 挪到 GPU，`weston` 空闲 CPU **0.0%**（pixman 时它是常驻 CPU 大户）；
  翻页/开列表的可感知延迟明显下降。
- 代价：`weston` RSS 从 ~40MB 涨到 ~48MB（SIZE 108MB→358MB，映射了 gl-renderer + EGL）；
  日志里多两条 `EGL_EXT_buffer_age not supported` / `swap_buffers_with_damage` 警告，无害。

### 6.7 关于 `EGL_PLATFORM_GBM_KHR` 的常量

写探测脚本时我把常量记错了，浪费了一轮（仅在用 EXT 入口时才需要）：

```
EGL_PLATFORM_X11_KHR     = 0x31D5
EGL_PLATFORM_GBM_KHR     = 0x31D7   ← 实测这台机器只有这个有效
EGL_PLATFORM_WAYLAND_KHR = 0x31D8   ← 别写成这个
EGL_PLATFORM_ANDROID_KHR = 0x3141
```

判据：client extensions 里有 `EGL_KHR_platform_gbm`。
另外 **GBM surface 的格式必须等于所选 EGL config 的 `EGL_NATIVE_VISUAL_ID`**，
不一致时 `eglCreateWindowSurface` 返回 `EGL_BAD_ALLOC(0x3009)`。
这台机器所有 config 的 visual id 都是 `0x34325241`（ARGB8888）。

## 7. D 状态进程的连锁灾难（weston 曾经卡死过）

现象：`fbdev-backend` 那次 weston **卡在 D 状态**（不可中断 IO 等待），
`ps` 里 `STAT=D`，`kill -9` 完全无效。然后：

- 它是 `emulationstation.service` **cgroup 里的进程** →
  `systemctl stop emulationstation` 会等 cgroup 里所有进程退出 →
  **永久挂住**（`timeout 15s` 直接 rc=124）。我前面一个探测脚本"卡住 5 分钟"就是死在这。
- 连 SSH 都被拖到发不出 banner（TCP 22 能连，banner 超时）。

教训：

1. **给会碰内核驱动的进程（weston / 显示服务）一律加 `timeout` 保护。**
2. **别把它放进会被 `systemctl stop` 的服务 cgroup 里**，否则停服务停不动。
3. 只能**长按电源键 10 秒强制重启**。能在开机前把 `config.ini` 的 `enabled=0`
   改掉（或提前改好），至少重启后直接进 ES，不会黑屏锁死。

## 8. 诊断过程中的其他雷（都踩过，别再踩）

| 雷 | 现象 | 正确做法 |
|---|---|---|
| `find /` | 扫进 4.4 G 的 `/roms`（exFAT/FUSE），把 TF 卡 IO 打满，SSH 直接失联 | 探查一律限定 `/usr /lib /opt /etc`，**绝不从 `/` 开始** |
| `pgrep -x emulationstation` | 永远匹配不到 | Linux `comm` 截断到 **15 字符** → 实际是 `emulationstatio`；用 `pgrep -f` 或 `ps -eo comm \| grep` |
| 用 `/dev/fb0` 判断"画面出来没" | 跑 `weston-simple-shm` 时 fb0 也**毫无变化** | 这块 rockchip DRM 上 fb0 不镜像 weston 的 scanout 缓冲。**别用它当判据**，直接问人或用 DRM ioctl 读 CRTC 的 fb |
| 并发挂 loop | e2e 偶发 `找不到 rootfs 分区（ext4/btrfs）` | 先 `losetup -a` 看有没有残留并清掉，再跑测试 |
| `__pycache__` | 单测 `import` 宿主模块时 Python 在 payload 里写 `.pyc`，被当成 payload 铺进镜像 | 加载脚本加 `sys.dont_write_bytecode = True`；注入器 `rsync --exclude='__pycache__/'` |
