# 阶段 2 —— 浏览器引擎选型与落地要点

阶段 1 已经把「开机不走 ES、走我们的启动器」这层做完了。
真正把网页画到屏幕上缺的是**渲染引擎**。这份文档说明为什么这步不简单、有哪几条路、以及推荐哪条。

---

## 1. 硬约束：dArkOS 上没有 X11，也没有 Wayland

这一点必须先认清。dArkOS 里 ES 的 systemd 服务是这样写的：

```ini
ExecStart=/usr/bin/emulationstation/emulationstation.sh
Environment="SDL_VIDEO_EGL_DRIVER=libEGL.so"
```

它是用 SDL2 + EGL 直接怼 DRM/KMS 全屏的，**没有桌面环境**。
所以：

- 不能简单 `chromium --kiosk` 了事——要先解决它往哪儿画
- 不能指望 `DISPLAY=:0`
- RK3326（Mali-G31）只有 GLES，没有像样的桌面合成器

另外这台机器的账还要算一下：RK3326 克隆机通常是 **1 GB 内存**、
720×720 或 640×480 屏、Cortex-A35 四核。
一个 Chromium 常驻就要 300-500 MB，放这儿是相当勉强的。

---

## 2. 候选方案对比

| 方案 | CSS 支持 | 内存占用 | 在 dArkOS 上的可行性 | 结论 |
|---|---|---|---|---|
| **cog (WebKitGTK) + DRM 后端** | flexbox / grid / CSS 变量都支持，够用 | 约 150-250 MB | `cog -P drm` 原生支持 DRM/KMS，不用 X11/Wayland；Debian 有 `cog` 和 `libwebkit2gtk` | **首选** |
| **Chromium + `--ozone-platform=drm`** | 最完整，前端就是照它调的 | 约 300-500 MB | Debian arm64 有 chromium，Ozone DRM 后端可用；但依赖体积大、启动慢（5-15 秒）、1GB 内存吃紧 | 备选，跑不动 cog 再上 |
| **Weston + 浏览器跑 Wayland** | 同 cog / chromium | 额外多一层合成器开销 | `weston_pkg_0.2.squashfs` 已经在 PortMaster runtimes 里，等于现成可用 | 折中：can 解决"浏览器只认 Wayland"的问题，但多一层 |
| **WPE WebKit + wpebackend-fdo** | 同 WebKit | 比 cog 更省 | 需要 Wayland 后端，得配 Weston | 极致优化时才考虑 |
| **NetSurf framebuffer** | ❌ 不支持 flexbox/grid | 极小 | 能跑，但布局会崩 | **不可用**：`index_v2.html` 整页靠 flex/grid/变量，NetSurf 渲染出来是一团乱 |
| **用 SDL2/Qt 重写一套原生界面** | — | 最少 | 性能最好、启动最快 | 工作量是移植的几十倍，等前面都不行再说 |

**推荐路线**：先试 `cog` + DRM 后端。它正好卡在"CSS 够用"和"内存吃得下"之间。
如果 cog 在设备上跑不出画面（WebKitGTK 对 Mali 的 EGL 有时会挑食），
再退到 chromium + Ozone DRM。

## 3. 除了渲染引擎，还有三件必须接的事

### 3.1 桥接：把 `window.AndroidBridge` 换成 Linux 实现

前端实际只用到 6 个方法：

```
getRomRoot()                 返回 ROM 根目录
listDir(dir, extsCsv)        返回 JSON 数组字符串
readText(path)               返回文本
readMediaDataUrl(path)       返回 data:...base64
launchRetroArch(rom, core)   启动游戏
executeShellCommand(cmd)     跑命令拿 stdout
```

前端是**同步调用风格**（`var s = AndroidBridge.readText(p)`），
所以不能在 WebKit 里用异步的 `messageHandlers`，改动量太大。
推荐做法：**起一个本机小 HTTP 服务**（Python 或 Go 都行，几十行），
`bridge-linux.js` 里用同步 `XMLHttpRequest` 请求它：

```js
var xhr = new XMLHttpRequest();
xhr.open('GET', 'http://127.0.0.1:8721/readText?p=' + encodeURIComponent(p), false);
xhr.send();
return xhr.responseText;
```

服务端对应的实现要点：

- **ROM 目录**：dArkOS 把游戏分区挂在 `/roms`
- **launchRetroArch 别自己瞎拼核心**：dArkOS 的 `/etc/emulationstation/es_systems.cfg`
  里每个机种都写好了完整启动命令（哪个核心、什么参数）。直接读它、按机种取命令来执行，
  这样游戏启动行为和原生 ES 完全一致，也不会出现"前端能进、游戏起不来"的割裂。
  `executeShellCommand` 这个方法就是为这个准备的——阶段 1 抓下来的
  `replace_file/darkos4es_systems.cfg` 可以直接拿来当参考。
- **状态显示**：dArkOS 已经有 `es-status-daemon.sh` 在往
  `/tmp/es-wifi-state`、`/tmp/es-bt-state` 写 WiFi/蓝牙状态（每 5 秒刷一次）。
  前端要显示状态图标的话直接读这两个文件，不用自己写探测。

### 3.2 手柄输入

网页前端靠键盘事件（方向键 / Enter / Esc）。
dArkOS 里本来就有一套手柄→键盘的映射工具：`/opt/inttools/gptokeyb`，
配置在 `/opt/inttools/keys.gptk`。

启动器拉起浏览器之前，要确认 `gptokeyb` 在跑并且映射符合网页前端预期。
注意 `emulationstation.sh` 里对 gptokeyb 的启停是包在 `boot_controls` /
`kill_boot_controls` 里的，正常开机路径**不会**调用它们——
所以 gptokeyb 是在别处拉起的，接入时需要实测确认它当时的状态，
必要时在我们的启动器里自己起一份。

### 3.3 分辨率与像素比

前端按 720×720 方屏设计（GAMTOS 那台是 720×720）。
但 dArkOS4Clone 面向的是一堆克隆机，屏从 640×480 到 720×720 都有。
浏览器启动参数里要能传分辨率，
`config.ini` 的 `browser_args=` 就是留这个口子的
（例如 `browser_args=-P drm --fullscreen --width=720 --height=720`）。

## 4. 落地顺序建议

1. **先只验证引擎能跑**：在设备上手动跑
   `/usr/bin/cog -P drm file:///opt/vagaretro/index.html`
   （或者 chromium 对应参数）。能看到画面、能翻页、帧率能接受，再往下走。
   这一步跟我们的启动器无关，纯粹测引擎可行性。
2. 引擎确认能用后，把它包成 `/usr/local/bin/vagaretro-browser`
   （启动器已经在按这个名字探测），此时开机就会自动进网页前端，
   `config.ini` 的 `browser_args` 用来调参数。
3. 接本机 HTTP 服务 + `bridge-linux.js` 真实实现，让游戏列表出来。
4. 接 `launchRetroArch`，让游戏能启动。
5. 最后做手柄映射调优、状态图标、开机动画衔接。

每一步都能单独回退：`config.ini` 里 `enabled=0` 就回原版 ES。
