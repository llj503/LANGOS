# 原生前端（C + SDL2/GLES2）方案与实测结论

> 2026-09-14 立。触发原因：用户反馈网页前端（WebKitGTK 2.28）**太卡**，
> 问"能不能复刻成 Linux 原生的"。选型结论：**C + SDL2 + GLES2 自绘**。

---

## 一、结论先行

**可行性已实测确认，不是纸上推演。** 在真机上（R36H ProMax / RK3326）：

| 验证项 | 实测结果 |
|---|---|
| 视频驱动 | `KMSDRM`（**不需要 weston**，像 ES 一样直接占 DRM） |
| 渲染器 | `opengles2`，`SDL_RENDERER_ACCELERATED` = **是(GPU)** |
| 最大纹理 | 8192×8192 |
| 中文渲染 | `/usr/share/fonts/truetype/droid/DroidSansFallbackFull.ttf` 全部正常 |
| 手柄 | SDL2 `SDL_IsGameController` = **1**，名字 `GO-Super Gamepad` |
| 空负载帧率 | **58.5 fps** |
| 300 张贴图 + 滚动 + 中文混排 | **59.4 fps**（vsync 锁 60Hz） |
| 300 张 168×136 纹理显存 | ≈ **26 MB** |
| 单张 640×480 JPEG 解码+上传 | **62.4 ms** ← 关键瓶颈数字 |

探测程序：`native/sdl-smoke.c`（驱动/渲染器/手柄/空载帧率）、
`native/sdl-probe2.c`（中文/贴图/真实负载帧率）。

## 二、为什么"原生会流畅"——卡在哪，说清楚

网页版的成本构成（前面几轮实测）：

| 环节 | 成本 |
|---|---|
| 15–20 张卡片插进 DOM | 87–97 ms（≈5 ms/张），纯 WebKit 布局 |
| 封面 | 中位 36 KB、平均 59 KB、最大 709 KB，**原图直喂** |
| 内存 | 300 张原图解码后几十~上百 MB 位图 |
| 引擎 | WebKit 2.28 **不支持 `contain` / `aspect-ratio`**，拿不到布局隔离 |

原生版把这三件事一次解决：

- **没有 DOM/布局引擎** —— 画面就是"往 GPU 提交 N 个四边形"，成本与卡片数量线性且极低
- **贴图常驻显存** —— 建一次，之后每帧只是 `SDL_RenderCopy`
- **可以自己控制解码时机** —— 放后台线程，滚动永远不等解码

## 三、架构：只换渲染层，后端逻辑全部复用

**这是整个方案里最重要的决定。** 前几轮踩坑最狠的部分
（平台映射、core 选择、ROM 递归扫描、`es_systems.cfg` 容错解析、
启动命令拼装、设置读写、卡二媒体桥）全在 Python 宿主里，
**一行都不用重写**。

```
┌─────────────────────────────┐
│ vagaretro-native  (C)       │  ← 新写的：只有 UI
│  SDL2 KMSDRM + GLES2        │
│  平台网格 / 游戏列表 / 搜索页│
│  设置页（待做）/ 手柄导航    │
└───────┬─────────────┬───────┘
        │ 读索引       │ 写启动请求
        ▼             ▼
   /opt/vagaretro/   /opt/vagaretro/launch.sh
   index.tsv         （**契约不变**）
        ▲
        │ 生成
┌───────┴─────────────────────┐
│ vagaretro-shell.py (Python) │  ← 原样保留，改成"数据服务 + 命令服务"
│  扫描 / 平台映射 / core 选择 │
│  启动命令拼装 / 设置读写     │
└─────────────────────────────┘
```

### 3.1 两个接口（都不新建概念，沿用已有的）

**① 数据索引**
Python 宿主扫完之后，除了现在给网页用的 `DIRS`，
再落一份 `index.json`：平台列表 + 每个平台的游戏（名字/路径/封面路径）。
C 端只读它，不做任何扫描。格式要**扁平、少嵌套**，避免 C 侧解析负担
（自己写个极简 JSON reader 就够，或者干脆用行式 TSV —— 更好解析）。

**② 启动请求**
沿用**现有契约**：前端往 `/opt/vagaretro/launch.sh` 写一个脚本、退出；
`vagaretro-front.sh` 的主循环发现它就 `bash` 执行，跑完回到前端。
C 端只要写这个文件，**游戏启动整条链路（含 SS/EASYRPG 的真实路径还原、
GBA 强制 mgba、N64/DC/NAOMI 的 cores_all）全部立即复用**。

设置同理：C 端不做 sysfs/amixer 细节，调一个小 helper 走 Python 的
`apply_setting()`。

### 3.2 与 weston 的关系：**不再需要 weston**

SDLKMSDRM 要独占 DRM master，和 weston 天然互斥。
所以原生版上线后，启动链路变成：

```
vagaretro-front.sh → vagaretro-native（直接占 DRM）
```

`native_available()` 那一整套探测（weston / python-gi / WebKit 绑定）
都可以退休。**顺带消灭了本轮那个"ES/别的 DRM 客户端抢 master
导致 weston 原子提交永久失效 → 全黑"的事故类型。**

> 但**不要立刻删掉 web 这条路**：两套渲染路径并存、用 `config.ini`
> 切换，原生版没打磨好之前网页版是保底。

## 四、渲染设计要点

### 4.1 缩略图缓存 —— 收益最大的一刀

实测：**单张 640×480 JPEG 解码+上传 62.4 ms**。一屏 60 张就是 3.7 秒，
这是网页版和原生版都要面对的同一个敌人。

做法：离线预生成。对每个平台扫一遍 `gamelist.xml` 里的 image，
统一缩到卡片尺寸（约 168×136，JPEG 质量 80），存到
`/opt/vagaretro/thumbs/<平台>/<hash>.jpg`。
- 解码量降一个数量级（640×480 → 168×136 是 1/13 的像素）
- 显存从"原图"变成固定 168×136×4 = 91 KB/张

### 4.2 虚拟滚动 + 异步解码

- 只对**视口内 + 上下各一屏**的卡片建纹理
- 解码放**独立线程**（SDL_Thread 或 SDL_AddTimer 分帧），
  主线程只做 `SDL_RenderCopy`
- 纹理池复用：滚出视口的纹理归还池子，不销毁重建

### 4.3 视口裁剪

`probe2` 里那行 `if (dst.y < -CARD_H || dst.y > 768) continue;` 就是全部秘密 ——
每帧只提交可见的 ~25 个四边形，GPU 侧压力可以忽略。

## 五、输入：直接用 SDL_GameController

**不需要再读 evdev**。实测 SDL2 把 `GO-Super Gamepad` 直接识别成
GameController，十字键/ABXY/Start/Select 都有标准映射。

> 注意：现有网页版是**直接读 evdev 喂前端**（见 skill 里那节），
> 因为 WebKit 拿不到裸设备。原生版没这个限制，可以用 SDL 的标准 API，
> 那套 evdev 代码在原生路径上不需要移植。

### 阶段 2 实况（2026-09-14）

**核心决定：启动逻辑一行都不重写。**

原生前端要起游戏，最直觉的做法是 C 里直接 `execv` RetroArch。**不要那么做。**
"这个平台的 ROM 该用哪条命令行"是平台相关的，而且差异很深：

| 平台 | 宿主里已经处理好的差异 |
|---|---|
| PS1 | 走 `/usr/local/bin/retroarch32` + 32 位那套 cores |
| saturn / nds / psp | 必须先 `realpath` 还原成 `/roms2/...`，否则包装脚本 `dirname "$2" \| cut -d/ -f2` 会抠到 `home` 而不是 `roms2`，yabasanshiro 直接启动失败 |
| EasyRPG | 要把 `.zip` 条目改成旁边的同名目录 |
| GBA | ES 首选核心是坏的，要靠 `FORCE_CORE` 压过去 |

这些规则宿主里都有一份，再在 C 里实现一遍就是第二份，**必然漂**。所以：

```
vgfront ──fork/exec──► python3 vagaretro-shell.py --launch <pid> <相对路径>
    │                            └─► 写出 /opt/vagaretro/launch.sh
    └─ 退出(0) ──► vagaretro-front.sh 的游戏循环看到 launch.sh
                      └─► bash launch.sh（起游戏）→ rm → 再拉起 vgfront
```

宿主那边只是加了一个命令行入口 `do_launch()`，内部直接调**网页版同款**的
`build_launch_script()`。C 只负责回答"用户点了哪个游戏"。

`--launch` **不扫 ROM、不起 weston**（只 parse 一次 es_systems.cfg），
所以按 A 到 launch.sh 落盘是**亚秒级**的，实测 0.45 s（其中大半是 python 启动）。

两个顺手做掉的东西：

- **「正在启动」遮罩**：从按 A 到模拟器真出画面之间有几秒纯黑，
  不给反馈玩家会以为没按上然后连按好几下（那几下会排队生成多个启动请求）。
- **续页状态** `/opt/vagaretro/.vgfront-state`：启动游戏要退出进程，
  回来时是新进程，默认落在主页第一项 —— 玩了某平台第 300 个游戏，
  退出来却回到主页，还得再翻回去。所以启动前存一份页面状态，下次起来读它，
  **读完就删**；用户主动退出（BACK）会把它删掉，于是下次**开机**仍从主页开始。
  实测：`1 2 0 0 0 5 0` → 下次起来 `[续页] 回到 FC / NES 红白机 的第 5 项`。

**验证方式**：真机上没法注入按键（没有 xdotool，手柄也不能模拟），
所以加了 `--launch N` 钩子 —— 它和真实按 A 走**同一个** `launch_game()`，
连 `g_gsel` 都同步过去，不存在"只在调试路径下对"。
配合 `native/launch-probe.sh`（只生成不执行，逐平台核对命令）和
`native/launch-e2e.sh`（端到端 + 负例 + 续页）三组脚本。

实测结论（`launch-probe.sh` 输出）：FC→`retroarch -L nestopia`、
GBA→`mgba`（`FORCE_CORE` 生效）、PS1→`retroarch32 -L pcsx_rearmed_neon`、
NDS→`/roms2/roms/NDS/...` + `choose_drastic_ver.sh`、
PSP→`/roms2/roms/PSP/...` + `ppsspp.sh` —— 五种形态全对。

### 阶段 4 实况：搜索页（2026-09-14）

**先说一个必须交代的事实：网页版这一页本身是个空壳。**

`#pageSearch` 在 `index.html` 里只有壳：

- `.search-input` 是个 `<div>`，不是 `<input>`；
- `.search-result-count` 永远写着 `0 款`，JS 里**没有任何地方更新它**；
- 按「搜索」键的分支是 `console.log('搜索:', input.textContent)`；
- 没有结果列表、没有过滤函数、也没有"按 A 启动"。

所以原生这版**不是"把网页版搬过来"**，而是按它的版式补成真能用的：
输入即过滤、结果列在下面、按 A 直接启动。这是本次唯一一处"超出网页版"的实现，
刻意如此 —— 照抄一个壳子没有意义。

**版式照抄 CSS**（`.search-panel` 1400 居中 / padding 40 / 圆角 20，
`.search-input` 高 56 圆角 12，`.keyboard` 10 列、键高 60 圆角 10，
`.keyboard-hint` 14px `--dim`），只有一处符号换掉了：

> ⌫ 是 U+232B，**NotoSansCJK 里没有这个字形**，实测渲染成 .notdef 方块
> （截图核对过）。换成 U+2190「←」—— 同一份字体里一定有，语义也是"往回删"，
> 顶栏那个「← 返回」用的就是它。这是踩过的第二个 .notdef 坑
> （第一个是整份 `DroidSansFallbackFull.ttf`）。

**取舍**（都写在 `vgfront.c` 的注释里）：

| 决定 | 理由 |
|---|---|
| 只匹配**游戏名**，不匹配平台名 | 匹配平台名时按一个 `F` 会一次命中几千条，结果列表就失去意义 |
| 结果上限 500 条 | 空关键词会命中全部 11001 条；500 条足够定位，`SR_NMAX` 一处改 |
| 每按一键**全量扫一遍**索引 | 11001 条做子串比较是亚毫秒级；比维护"收窄上一次结果"少一半代码，也少一半出错的地方 |
| 匹配只折叠 ASCII `a-z` | 中文名字节（>=0x80）原样比，所以 `1941` 能命中「1941 Counter Attack」，中文名也不会被折坏 |
| 结果列表是**新增**的 | 网页版没有。放在面板下方、可滚动、复用游戏卡的观感 |
| 输入框里的光标竖线 | 只在焦点落在软键盘上时画，对齐网页版 `:focus` 的观感 |

**按键映射**（`handle_key` 里搜索页那一支）：

| 输入 | 行为 |
|---|---|
| Y（主页/游戏页） | 进搜索页。底栏第 4 项写的就是「Y 搜索」，网页版键盘也是 `y → showPage('search')` |
| 方向键 | 软键盘上按 10 列网格移动；在最后一行继续 ↓ 就进结果列表 |
| A | 键盘上 = 按下那一格（字符 / ← / 清空 / 搜索）；结果列表上 = **启动这个游戏** |
| B（手柄 B 键） | 结果列表上 = 回软键盘；键盘上 = 退格；输入已空 = 返回上一页 |
| START | 清空输入 |
| SEL(back) | 返回上一页 |

返回落点会记来源：从游戏页按 Y 进搜索，退回来还是那个游戏列表（`g_search_from`）。

**续页**：`/opt/vagaretro/.vgfront-state` 多存了第 8 个字段（搜索串），
所以"搜到一半去玩、退出来输入串和结果都还在"。旧格式（7 字段）照样能读 ——
`fscanf` 少读一个字段不算错。

**本次新增的两件验证手段**：

1. **`--keys SEQ` 按键序列钩子** —— 真机上没有 xdotool，没法注入按键。
   它每帧喂一个按键，**直接调 `handle_key()`**（不是旁路），于是
   "软键盘导航 → 输入 → 退格 → 进结果 → 启动"整条链能在真机上自动跑。
   字符表：`L R U D` / `A` 确认 / `B` 退格 / `T` TAB / `Y` 搜索。
2. **`--search Q` / `--sfocus N`** —— 直接落到搜索页并预置输入串与焦点，
   供截图脚本一步到位。

配套脚本：

- `native/try-search.sh` —— offscreen 出三张图（空输入 / 有结果 / 无结果），
  **不碰 DRM**，不用停设备上跑着的前端；
- `native/try-search-e2e.sh` —— 交互链五步（Y 进页 / 输入 M / 退格 / 从结果启动 / 续页）；
- `native/try-search-kms.sh` —— 在真显示路径（KMSDRM）上跑一次并截图，
  跑完按原状态恢复前端。

**实测结果**：`--keys YDRRA` → `[搜索] 「M」→ 500 条（到上限）`；
`YDRRAB` → 再追加 `[搜索] 已清空`；`--search M --keys DDA` →
`[启动] FC / NES 红白机 / Tecmo超级碗大赛[英].zip` + 写出 `launch.sh`（核心 nestopia）；
重新拉起 → `[续页] 回到搜索页「M」(500 条)`。
KMSDRM 截图与 offscreen 结果一致（渲染器 `opengles2 加速=是`）。

**一个副作用要注意**：`--keys` 走到「结果列表 + A」时会真去写 `launch.sh`。
所以脚本里每步之前都先 `rm -f` 它，免得外层启动器真的把游戏拉起来。

**顺带发现（本轮没改）**：索引 `G` 行的标题带扩展名（`Konami冰球[美].zip`），
所以游戏列表页和搜索结果都会显示 `.zip`。这是宿主 `_scan_roms()` 里
`"title": name` 的原样行为，网页版吃的是同一份数据 —— 要改得动索引生成，
影响面比这一页大，先记在这里。

## 七、工具链（这台机器上怎么编译）

**不需要交叉编译 —— 设备自带 gcc/g++/make/pkg-config。**
但 `/usr/include` 被镜像精简过：SDL2 和 libc 的开发头文件都没了
（`dpkg` 数据库里却记着 `libsdl2-dev` 是 installed，实际文件只剩 23/若干）。

`native/dev-env.sh` 的做法：`apt-get download` 只下 .deb（**不装、不改系统**），
`dpkg -x` 解到 `/opt/vagaretro/sdl2dev`，编译时 `-isystem` 指过去。

```bash
source /opt/vagaretro/native/dev-env.sh
gcc $VG_CFLAGS -Wall -o /tmp/foo foo.c $VG_LDFLAGS -lSDL2 -lSDL2_ttf -lSDL2_image
```

要求下载的包：`libc6-dev` `linux-libc-dev` `libsdl2-dev`
`libsdl2-ttf-dev` `libsdl2-image-dev`（Ubuntu **eoan**，走 old-releases）。

> **踩坑**：链接符号要单独建 `$DEV/lib`，只放 SDL 系列的三个软链。
> 如果直接把 `$DEV/usr/lib/aarch64-linux-gnu` 加进 `-L`，
> 解出来的 libc6-dev 里的 `libc.so` 会混进 ld 的搜索路径。
> （`crt1.o`/`Scrt1.o`/`libc.so` 系统里本来就有，只缺头文件。）

## 九、决定性证据：网页方案在 wayland 下**注定**软件渲染

> 2026-09-14 重启后实机取证。这一节是原生方案的**根据**，不是补充说明。

### 现象

重启后 `journalctl` 里有两条：

```
emulationstation.sh[577]: file /dev/mali0 is not of a compatible version (user 10.6, kernel 11.7)
```

同时 `WebKitWebProcess` **没有**打开 `/dev/mali0`（`fuser` 显示只有 weston 持有），
且**静态画面下就常年吃 10% CPU**。

### 取证

设备上并存两个 libmali：

| 库 | DDK | 编译期 winsys | 内核接口版本 |
|---|---|---|---|
| `/usr/lib/aarch64-linux-gnu/libmali-bifrost-g31-rxp0-wayland-gbm.so` | r6p0 (2020-02) | `wayland,gbm` | **10.6 ← 内核不认** |
| `/usr/local/lib/aarch64-linux-gnu/libmali-bifrost-g31-rxp0-gbm.so`   | r13p0 (2021-03) | `gbm` | **11.7 ✓** |

系统默认的 `libEGL.so` / `libEGL.so.1` / `libGLESv2.so` / `libmali.so`
**全部软链到 r6p0 那一份**，而内核 kbase 要求 11.7。

`native/egl-probe.py` 在 weston socket 下实测（`env XDG_RUNTIME_DIR=/run/vagaretro
WAYLAND_DISPLAY=wayland-vagaretro python3 egl-probe.py`）：

```
系统默认 libEGL.so.1 (-> r6p0)   eglGetDisplay=0x3ab7aa90  eglInitialize=0  err=0x3001 (EGL_NOT_INITIALIZED)  → 失败
备选 r13p0 (winsys=gbm)          eglGetDisplay=NULL        err=0x3000 (EGL_SUCCESS)                           → 失败
```

跑 r6p0 那一路时，探针进程自己把上面那两行 `mali0 版本不匹配` 打了出来 ——
**报错来源坐实就是 r6p0，闭环。**

### 结论（硬约束）

**wayland 客户端在这台设备上拿不到 GPU。** 用 `eglGetPlatformDisplayEXT`
显式问一次，两个库各自缺什么一目了然：

```
r6p0  (winsys=wayland,gbm)   EGL_PLATFORM_WAYLAND -> 支持      EGL_PLATFORM_GBM -> 不支持
r13p0 (winsys=gbm)           EGL_PLATFORM_WAYLAND -> 不支持    EGL_PLATFORM_GBM -> 不支持
```

- **r6p0** 有 wayland platform、display 能建出来，但 `eglInitialize` 失败
  （`err=0x3001`）—— **DDK 10.6 对不上内核要的 11.7**；
- **r13p0** DDK 匹配，但**编译期就没编 wayland winsys**，连 display 都拿不到。

所以 weston 里的一切客户端（WebKit）只能：
**CPU 渲染 → `wl_shm` buffer → 交给 weston 用 GPU 合成。**

这一条直接解释了此前所有"卡"的观测：15-20 张卡片插入 DOM 要 87-97ms、
静态画面 10% CPU、滚动丢帧。
**这不是能靠调 CSS / 减 DOM / 压图优化掉的。**

> **根因说准一点**：不是"内核挑食"，而是设备上缺一份
> **「`winsys=wayland` 且 `DDK >= 11.7`」的 blob**。
> 现有的两份各满足一半，凑不齐。

### 补验：把库路径指对能不能救？——不能

`native/run-egl-probe.sh` 对比了三种环境：

| 环境 | `dlopen("libEGL.so.1")` 解析到 | 结果 |
|---|---|---|
| A 无 `LD_*`（= WebKit 现状） | `/usr/lib/.../libEGL.so.1` → r6p0 | 失败 |
| B 带 `LIBPFX` + 软链 | 指向 **r13p0** | **仍失败** |
| C 只带 `LIBPFX`（无软链） | `/usr/lib/.../libEGL.so.1` → r6p0 | 失败 |

B 组是关键：**库指对了依旧起不来**，因为 r13p0 压根没有 wayland platform。
这不是路径配置问题，是 blob 本身不具备该能力。

### 附带发现：r13p0 的 gbm 需要独占 DRM

探针在 **weston 正在运行**时，连 r13p0 的 `EGL_PLATFORM_GBM` 也拿不到（返回 0）
—— 因为 weston 已占着 `/dev/dri/card0`。weston 自己能用，是因为它第一个起来、
握着 DRM master。

> **对原生方案的直接影响**：SDL2 的 KMSDRM 后端同样需要 DRM master，
> 所以原生前端启动时**必须先停 weston**，两者不能共存。
> 这条要落到阶段 5 的启动器改造里。

### 反向印证

原生方案之所以在探针里跑出 58.5 / 59.4 fps，正是因为
**SDL2 的 KMSDRM 后端直接占 DRM + 走 gbm winsys** ——
用的就是唯一匹配内核的 r13p0，完全不经过 wayland。

### 推论（对后续排期的约束）

- 网页版**保留作保底即可，不要再为"流畅度"投入**，它的上限是"能用"。
- 换 weston 后端（pixman / 软件合成）**救不了** —— 瓶颈在客户端侧，不在合成侧。
- 理论上可解：Rockchip 命名规范里确实有 `-wayland-gbm` 变体（设备上 r6p0 那份就是），
  找一份 r13p0 的 `libmali-bifrost-g31-rxp0-wayland-gbm.so` 换上就能救。
  **但不做**：① blob 能否找到、是否真兼容 kbase 11.7 都不确定；
  ② 一旦不对，**整个显示栈（weston + 前端 + ES）一起挂**，只能 SSH 或重刷卡救回来；
  ③ 换来的只是"让保底方案快一点"，而原生方案本就不受影响。**收益配不上风险。**


## 十、RA 热键与 NDS 独立模拟器（2026-09-14 现场修正）

### 白屏：最后排除掉"启动链路"，锁定到"两个 DRM 客户端抢 plane"

三组对照录出来的画面**字节完全相同**（`3430 字节，md5=d7f73c8f`，纯白）：

| 组 | 命令 |
|---|---|
| A | 原厂 `/usr/local/bin/retroarch`（bash wrapper，ES 用的就是它） |
| B | 我们直连的 `/opt/retroarch/bin/retroarch -c ... -L <core>` |
| C | B + 强制 `LD_LIBRARY_PATH` 指到 SDL2 2.0.10 |

**A/B/C 全白 ⇒ 跟"谁拼的启动命令"无关。** 顺带排掉了 `video_threaded`、shader、
`video_driver=glcore`、`video_fullscreen_x/y`、`video_waitable_swapchains`、gbm shim。

判据在 DRM 层 —— `/sys/kernel/debug/dri/0/summary` 的 `buf[0].addr`：

| 谁在跑 | win1-0 | buf addr | 屏幕 |
|---|---|---|---|
| vgfront（SDL kmsdrm） | ACTIVE | `0x604000`（有效） | 正常 |
| retroarch（gl / kms） | ACTIVE | 有时 `0x900000`→`0x600000`，有时 `0x00000000` | 白 |

plane 还是 ACTIVE 但 `addr = 0` = **VOP 在扫地址 0 的垃圾内存**，这就是白屏的真身。
另外 `fuser -v /dev/dri/card0` 抓到过 **两个客户端同时持有**（`drastic` 与 `vgfront`）——
游戏跑起来之后前端又被拉起，两个 GL 客户端抢同一个 CRTC / CRTC 被反复 enable。

**操作规范（重要）**：游戏运行期间**绝不能** `pkill vgfront` 或重启 `vagaretro-front.sh`。
要动显示相关的东西之前，先 `ps -ef | grep -E '[v]gfront|[r]etroarch'` +
`fuser -v /dev/dri/card0` 看清有几个客户端，只撤掉多余的那个，**不要碰游戏进程**。

### 客观抓屏：`ffmpeg -f kmsgrab`

这台镜像自带 `ffmpeg` 且**带 kmsgrab**，可以直接抓 VOP 正在扫的 primary plane，
不依赖任何应用自己截图（应用自己的截图可能是假的 —— retroarch 截出来是 3430 字节纯白）：

    ffmpeg -f kmsgrab -i - -frames:v 1 -vf 'hwdownload,format=bgr0' -y out.png

⚠ 输出格式写 `bgra` 会报 `Invalid output format bgra for hwframe download`，要用 **`bgr0`**。
（`modetest` / `fbgrab` / `scrot` / `v4l2-ctl` 这台机器都没有；`/dev/mem` 被 STRICT_DEVMEM 挡，
`dd if=/dev/mem` 读出来是 0 字节 —— 别在这条路上浪费时间去判断"屏幕到底是不是白"。）

### RA 热键：被改掉了，恢复成 dArkOS 原生

**根因**：`input_enable_hotkey_btn` 被改成了 `"16"`（MODE），而 dArkOS 原生是 **`"12"`（SELECT）**。
热键不是 SELECT，于是 Select+X / Select+Start 全都无反应。

原生值取自镜像自带的 `retroarch.cfg.bak`：

| 组合 | 键（retropad id） | 现状 |
|---|---|---|
| Select + Start | enable_hotkey `12` / exit_emulator `13` | exit 本来就是 13 ✅ |
| Select + X | menu_toggle `2` | ✅ |
| Select + R1 / L1 | save_state `5` / load_state `4` | ❌ 被改成 R2/L2（`7`/`6`） |
| Select + B | reset `0` | ❌ 被清成 `nul` |
| Select + A | screenshot `3` | ❌ 被清成 `nul` |
| Select + Left | toggle_fast_forward `14` | ❌ 被改成 `5` |

restore 脚本：**`/opt/vagaretro/set-hotkeys.sh`**（幂等，可随时重跑；自动备份 `*.pre-hotkey-<ts>`）。
做法是「把旧的 `_btn` 行全部用 `;` 注释掉 + 在文件末尾追加一份生效定义」——
这样不管 RA 解析重复键时是"先出现者胜"还是"后出现者胜"，结果都一样（dArkOS 自己也是用 `;` 禁用）。

⚠ dArkOS 的 BaRT 恢复菜单（`/usr/bin/emulationstation/emulationstation.sh`）自己会 `sed`
这两个文件，被改回来了就再跑一次脚本。两个文件都要改：`retroarch.cfg` 和 `retroarch32/retroarch.cfg`。

### NDS：一律走独立模拟器 drastic（用户指定）

在 `vagaretro-shell.py` 里加了 `FORCE_EMULATOR = {"NDS": "drastic"}` —— 与 `FORCE_CORE` 并列，
但选的是**"用哪个模拟器程序"**而不是"RA 里的哪个核心"（所以它可以把 %EMULATOR% 换成 standalone）。
拼出来的命令：

    sudo perfmax performance <真实路径>; nice -n -19 \
        /usr/local/bin/choose_drastic_ver.sh drastic <真实路径>; sudo perfnorm

三个要点：
- **必须传真实 ROM 路径**，不能传兼容软链树 —— `drastic.sh`（和 saturn.sh 同一个套路）
  用 `dirname "$1" | cut -d/ -f2` 抠出卡名（`roms2`）去建 `savestates/cheats/slot2` 软链，
  路径错了存档就散在 `/home/` 下面。这条由 `STANDALONE_SYSTEMS` 的 realpath 还原覆盖。
- `%CORE%` 在强制换模拟器时必须清空（standalone 的 .sh 大多不用它，n64.sh 拿它当开关）。
- 另加 `STANDALONE_DIRECT`：即使 `es_systems.cfg` 的 nds 段被删/被改，
  点 NDS 游戏也照样起得来（`direct_command()` 平时对 standalone 是直接认输的）。


## 十一、手感修正：A/B 反了、版式偏小、L/R 切分类（2026-09-14 用户反馈）

### 1. A/B 是反的 —— 根因是设备硬件布局与 SDL 默认相反

用户原话："前端界面 ab 是反的总容易误触"。查下来**不是代码写错，是信了 SDL 的默认**：

| | 物理 A | 物理 B | 物理 X | 物理 Y |
|---|---|---|---|---|
| **原厂 ES**（`/etc/emulationstation/es_input.cfg`） | id **1** | id **0** | id 2 | id 3 |
| **SDL 默认**（evdev 约定） | b0 | b1 | b2 | b3 |

这台 GO-Super Gamepad 的物理 A 键在 evdev 上是 **b1**、物理 B 是 **b0** ——
跟 SDL 的"BTN_SOUTH(0x130)=A"约定正好相反，原厂已经手工纠正过。
我们的 `pad_add_mapping()` 照抄了 SDL 默认，于是界面上确认/返回整个反过来。
**没改代码里的语义**（仍是 A=确认、B=返回），只把映射表里的 raw button 对调：

    "a:" PAD_RAW_A ",b:" PAD_RAW_B ...    /* PAD_RAW_A=b1  PAD_RAW_B=b0 */

⚠ X/Y **不要动** —— ES 的 x=2/y=3 与 SDL 的 x:b2/y:b3 一致，真调过的话 ES 那边也会是反的。

**以后加键先跟 `es_input.cfg` 对一遍**，别信 SDL 默认；`es_input.cfg` 是原厂在这台机器上
逐键按出来的，是唯一权威。

自证手段：代码里加了 `pad_dump_bindings()`，开手柄时把 A/B/X/Y/START/BACK 的
**实际绑定**打出来（`SDL_GameControllerGetBindForButton`）：

    [pad] A     -> raw b1      [pad] B     -> raw b0
    [pad] START -> raw b13     [pad] BACK  -> raw b12

A/B 到底反没反，看这行字就行，不用靠人按了猜。

### 2. 底栏提示写着「SEL 分类」，按下去却是退出前端

底栏原来是 `{X 收藏}{SEL 分类}{STA 设置}`，而代码里：**X 什么都不做、
SEL = 退出前端、STA 才是切分类**。用户照着底栏按 SEL 想切分类，前端直接退了 ——
这是"容易误触"的另一半来源。

改成 5 项，且**每一项都真有那个功能**：

    {A 进入} {B 返回} {Y 搜索} {L/R 分类} {SEL 退出}

没实现的（X 收藏、STA 设置页）宁可不标 —— 标了按下去没反应比不标更糟。
**规则：底栏写什么就得真是什么，加提示前先确认那条分支存在。**

### 3. 版式：主页 4→3 列，游戏列表 5→4 列（用户要求"太小"）

| | 网页版 CSS 原值 | 现在 | 卡片宽 | 封面高 |
|---|---|---|---|---|
| 主页平台网格 | `repeat(4,1fr)` | **3** | 219→300 | 固定 170 |
| 游戏列表 | `repeat(5,1fr)` | **4** | 176→224 | 235→299 |

原生前端改 `PG_COLS` / `GAME_COLS` 两个宏即可（导航、滚动、`ensure_visible`
全是从宏推的，自动跟随）。

**网页版（`renderer=native` 的回退路径）要改 5 处，少一处就是上下键跳错行**：
`index.html` 的 `.platform-grid`、`.game-chunk` 两处 CSS，
`GAME_COLS` 常量，以及 `handleNavigation()` 里 pageHome / pageGames 的两个 `cols`。
（网页版这份改动**未在真机跑过** —— 当前 `renderer=auto` 走 sdl，网页版是回退路径。
已备份设备原文件到 `/opt/vagaretro/backup/index-<ts>.html`。）

### 4. 顶栏分类：加手柄 L1/R1

用户原话："顶栏 lr 不能切换了"。查下来原生前端从来只绑了 **START**（键盘 TAB），
L1/R1 没有任何分支 —— 而方向键左右在主页是"在卡片之间挪"，不碰分类。

新增 `cat_step(int d)`，三个入口共用一份逻辑（键盘 TAB / 手柄 START / L1 R1）：
改分类下标 → 复位选中与滚动 → `build_view()` → `mark_dirty()`。
**只在主页生效**（内部自己判 `g_page`），游戏页/搜索页按 L/R 不会偷换分类。

    case SDL_CONTROLLER_BUTTON_LEFTSHOULDER:  cat_step(-1); return;
    case SDL_CONTROLLER_BUTTON_RIGHTSHOULDER: cat_step(+1); return;

### 5. 自启链路是常驻的：杀了 `vagaretro-front.sh` 会被自动拉起来

我为了换新二进制 `pkill` 掉前端，结果**同时出现了两个 vgfront 抢 `card0`**。

原因：`/usr/bin/emulationstation/emulationstation.sh`（pid 6611，父进程 1）是**常驻的**，
它守着 `vagaretro-front.sh`；外层一退，它立刻重新拉一份。我又手动 `setsid` 起了一份，
于是两份同时在跑。

**规范**：
- 换二进制后**不要**手动再起启动器 —— `pkill` 掉 `vgfront`（或启动器），
  等约 15 秒，`emulationstation.sh` 会自己拉一份新的起来；
- 真要确认，先 `ps -ef | grep -E '[v]gfront|[v]agaretro'` 与 `fuser -v /dev/dri/card0`
  看清**只有一条链**；
- `pkill -f` 匹配整条命令行，会把自己也匹配上 —— 用 `'[v]agaretro-front.sh'` 写法；
- 主循环把 vgfront 的**退出码**当判据（0 才 continue），`SIGTERM` 的 143 会让启动器
  一起结束 —— 想干净重启就连启动器一起重启。脚本见 `native/front-restart.sh`。

### 6. 客观抓屏终于可用：`kmsgrab` 的格式参数是 `bgr0`

上一轮记的 `-vf 'hwdownload,format=bgra'` **会失败**（`Invalid output format bgra
for hwframe download`），正确的是 **`bgr0`**（对应 XRGB8888）：

    sudo ffmpeg -hide_banner -loglevel error -f kmsgrab -i - -frames:v 1 \
        -vf 'hwdownload,format=bgr0' -y /tmp/kms-now.png

这条通了意味着**"屏幕现在到底显示什么"可以自己看，不用再问用户**。
脚本 `native/screen-grab.sh`（**只抓屏，不杀任何进程** —— 之前的 `kmsgrab.sh`
开头就 `pkill retroarch`，在用户玩游戏时会把人踢出去，已废弃不再用）。
